## 1. 这条片子长什么样

| 段 | 素材区间 | 速度 | 时间线 | 内容 |
|---|---|---|---|---|
| **s1** | 0.30 → 8.90s | 1.0× | 0 → 8.600s | 开场四杀：素材 1.43 / 2.10 / 4.67 / 7.33s |
| **s2** | 8.90 → 19.055s | **1.5×** | 8.600 → 15.370s | 空档推进，收在 19.900 / 20.767s 的双杀上 |

- **只有 1 个切点**（8.600s），且**切点落在 BGM 的第 5 小节起点**上，用 **2 帧黑场素材**藏住。
- 白闪 ×2（素材 2.100s → 时间线 1.800s；素材 4.667s → 时间线 4.367s），都是 **2 帧白场素材**。
- 曝光特效打在所有 4 次击杀上；瞬间模糊 + 回弹摇摆只打在两次"较大"的击杀上（克制）。
- 全片一层调色：**青橙** 65 + 暗角 10 + 噪点 5 + 精细锐化 10。

> **为什么"零切割 + 1.5× 掠过"而不是多切几刀？**
> 你的集锦定义是「保证每个原始素材先后一致，不要把片段切割太碎」（`styles/game-montage.md` §一）。
> 空档**不剪掉**（剪掉就会出现跳切），而是用 1.5× 压过去——两个要求同时满足。
> 代价是这一条的切点密度只有 **3.9 切/分**，远低于参考成片的 20–38 切/分；
> 这是"一次交火完整呈现"与"多镜头狂切"两种形式的差别，不是参数没调好。

## 2. BGM 是怎么来的（这条值得单独看）

**剪映曲库不能被程序引用。** `pyJianYingDraft` 的 `AudioSegment` 只收本地文件，
导出时 `type` 硬编码成 `extract_music` / `category_name: "local"`
（`references/environment.md`）——所以"在草稿里写一条曲库音乐"这条路在技术上是堵的。

**但你在剪映面板里试听/下载过的曲子会留在本机**，而且剪映顺手把**拍点**也算好了：

```
%LOCALAPPDATA%\JianyingPro\User Data\Cache\music\
   4fdd1e597bbee84e50c338446f38ddca.mp3      ← 音频本体（169.69s）
   18f53e55c53d8c446682d17187cddabe.beat     ← 剪映算的拍点：time(ms) / value(拍号) / energy
   downLoadcfg                               ← 下载台账（可看出下载先后）
```

> ⚠️ `.beat` 的文件名 hash 和 mp3 的文件名 hash **不是同一个** —— 3 份 `.beat` 里
> **0 份**能按同名配到 mp3。只能按「时长 − 末拍点」最近来配对。

本次选中的就是**你 9/14 下载的那首**（缓存里最新的一首）：

| 项 | 值 |
|---|---|
| 曲目 | `4fdd1e59…mp3`（剪映曲库缓存） |
| BPM | **≈125**（从剪映拍点中位拍距 480ms 反算；项目调研给的电子竞技区间是 120–140） |
| 取段 | **15.350s → 30.720s**，正是该曲**第 8 小节的 drop**，8 小节整 = 15.37s |
| 段内拍点 | 33 个（1 拍 0.48s），小节起点 0.00 / 1.92 / 3.83 / 5.76 / 7.70 / 9.60 / 11.52 / 13.45s |
| 落盘 | `projects/game-001/bgm/jy_4fdd1e59_drop.wav`（48kHz 立体声，**未做归一化**） |
| 拍点表 | `projects/game-001/bgm/jy_4fdd1e59_drop.beats.json` |

**拍点对齐实测**（压白闪的那两次击杀，相对最近拍点的偏差）：

| 击杀（素材） | 时间线 | 偏差 |
|---|---|---|
| 2.100s | 1.800s | 0.120s（不到 1 拍，约 0.19 拍） |
| 4.667s | 4.367s | 0.057s |

> 我**没有**为了让偏差变成 0 去移切点：EDL 的切点精度上限本来就是 ±0.1s（`CUT-05`），
> 而击杀时刻是素材事实，不该被拍点拖动。**0.12s @125BPM 是听不出来的**。

⚠️ **原曲母版已经削波**（真峰 **+0.97 dBFS**）。这不是本步骤引入的，是那首曲子自己的问题，
底下也没法还原。所以 §5 的人工清单里有"响度统一"这一项。

`projects/game-001/bgm/*.wav` 在 `.gitignore` 里（版权 + 体积）。
**换机器要复现 BGM**，跑这条命令（读你本机剪映缓存，不改任何东西）：

```powershell
.venv\Scripts\python.exe projects\game-001\tools\pick_bgm_segment.py `
  --src "$env:LOCALAPPDATA\JianyingPro\User Data\Cache\music\4fdd1e597bbee84e50c338446f38ddca.mp3" `
  --beat "$env:LOCALAPPDATA\JianyingPro\User Data\Cache\music\18f53e55c53d8c446682d17187cddabe.beat" `
  --start 15.35 --dur 15.37 `
  --out "projects\game-001\bgm\jy_4fdd1e59_drop.wav"
```

**版权提醒**：这条曲子的音轨来自剪映曲库，**只在剪映的授权范围内可用**。
`.gitignore` 排除它是刻意的（第 8 轮曾把两首完整商业歌曲误提交进公开仓库，已回退）。
发布前请自己确认平台对这首曲子的授权状态。

## 5. ⚠️ 必须由人做的事（EDL 表达不了，我**没有**假装做了）

| # | 事项 | 为什么不能自动 | 怎么做 |
|---|---|---|---|
| 1 | **导出** | 剪映 7+ 无自动导出接口 | 人工点导出 |
| 2 | **曲线变速（闪进 0.1×）** | `operations.md` §3.4 标「❌ 未表达」，EDL 只有恒速 `speed` | 若要更"瓦"的手感：在 4 次击杀**前 2 帧**加闪进，击杀瞬间回 1×。**这是本项目看家手法，但没做** |
| 3 | **接缝两侧音频交叉淡化** | EDL 只表达 `fade.in/out`，不含"切口两侧各 2 帧交叉" | 8.600s 处音频切一刀，两侧各加 2 帧淡化，防咔哒声 |
| 4 | **响度统一** | 需要试听 + 真峰值表 | 目标 **−14 LUFS / 真峰 ≤ −1 dBTP**。现在预览是 −10.8 LUFS，偏响；且**源曲母版已削波（+0.97 dBFS）**，信息已丢，建议在剪映里给 BGM 挂"响度统一"再压 2–3 dB |
| 5 | **混音比例复核** | 需要耳朵 | 现在是 BGM 0.70 / 游戏原声 0.16。曲库原曲比自合成 BGM 响得多（段 RMS −4.6 dBFS），觉得压住了枪声就把游戏原声提到 0.25 |

## 6. ⚠️ 本轮推翻的一个既有结论（**请重点看**）

**`analysis2/kills_mine_measured.json` 这个"击杀清单"有误报。**

我按 skill 的纪律（`kill-extraction.md`：任何提取类判据上线前必须目视核对）
把 `4c58efb4` 的击杀时刻放大到能读 UI 的程度，结果：

| 信号报的击杀 | 目视看到 |
|---|---|
| 素材 **1.433s** | 右上角 **5 个敌人头像全亮** —— **没有人阵亡** |
| 素材 **2.100s** | 有击杀播报（可信） |
| 素材 4.667s | 击杀播报位有变化（可信度中） |
| `b61cc53d` **6.2s** | 右上角只有 **4 个亮**，而 10.0s 是 **5 个** —— **位置对不上** |

我**试着做了一个更好的判据**（`count_enemy_hud.py`：数"存活敌人数"，
阵亡头像会**去色变灰** ⇒ 用饱和度当判据，与切点无关）：

- v1 全局亮度阈值 → ❌ 受击态（血条变红）把存活判成阵亡，存活数在 2~5 之间乱跳
- v2 逐头像时间维归一化 → ❌ 灰度差被 HUD 渐变底吃掉
- v3 饱和度 → 存活 ≈54 / 阵亡 ≈14，**分离明显**，但**受击/治疗时仍会抖**
  ⇒ **结论：可以作为"人看台账"的辅助，还不能当自动判据。**

**所以这条片子里的击杀时刻，仍然是信号判据给的，我只在两次白闪上做了目视确认。**
把这件事写出来，是因为"信号自证不算验证"本项目已经栽过一次；这次至少把边界说清了。

> 下一步该做的：做一份**人工标注的击杀 ground truth**（几条素材逐帧看完），
> 再用它去标定自动判据。在那之前，`kills_mine*.json` 只应被当作**候选清单**。

### 关于"能不能直接调剪映的曲库接口"

我从本机 `VECreator.dll` 的字符串表里挖出了曲库相关的接口路径
（`/lv/v1/search/songs`、`/lv/v1/get_collections`、`/lv/v1/get_collection_songs`、
`/lv/v1/music/similar_music_rec`），并实测了三个 API 域名：

```
403  POST https://lv-api.ulikecam.com/lv/v1/search/songs
403  POST https://lv-api.ulikecam.com/lv/v1/get_collections
404  POST https://lv-api.ulikecam.com/lv/v1/music/similar_music_rec
```

**403 = 缺客户端的签名头**（剪映走字节的 `X-Argus/X-Gorgon` 一类风控签名）。
**我不去逆向那套签名** —— 那是绕过商业软件的技术保护措施，
和本项目第 1 轮拒绝解密草稿是同一个立场（`docs/lessons.md` 第 1 轮 §3）。
所以走的是**你本机缓存**这条合法且稳的路。
