# frame-probe —— 抽帧偏差测量器

回答一个容易被跳过的问题：**「按时间抽帧」的工具，输出的第 k 帧真的对应源时间 k/R 秒吗？**

- 脚本：`measure_sampling_bias.py`（自带不变量自测）
- 结论（本项目实测）：`-vf fps=4` 在三段素材上都存在约 **+0.105s 的单边系统偏差**，**与 CFR/VFR 无关**

生成日期：2026-09-12 ｜ 作者：creative-reviewer

---

## 1. 为什么需要它

`projects/game-001/analysis/verify/` 里有 76 张按时间码命名的复核帧，是全项目最可靠的时间码证据。
但同一份分析里另有 `frames/`（4fps 连续抽帧）。**如果抽帧工具本身有系统偏差，
那么任何基于"第 k 帧 = k/4 秒"的推断都会整体偏移，而且看不出来。**

这类偏差的隐蔽之处：它**不会报错、不会让画面看起来不对**，只是让每个时间码整体平移一点。
本项目已经撞到过三个同类失败（`tim()` 微秒陷阱、ebur128 进度行、VFR 补帧），
共同特征都是**「工具静默地重解释了单位或序号，而结果表面正常」**。

---

## 2. 方法：逐像素匹配求真实来源

核心思路：**不比时间码，比内容。** 拿到每个输出帧的"真实来源帧"，再跟标称时间比。

| 步 | 做法 |
|---|---|
| 1 | **基准**：用 `-fps_mode passthrough` 解码源视频 → 帧序与容器一一对应的源帧序列；用 `showinfo` 取每帧真实 `pts_time` |
| 2 | **待测**：用待测滤镜（如 `fps=4`）抽出输出帧 |
| 3 | **匹配**：对每个输出帧，在「标称源帧号 ± 14 帧」窗口内逐帧算平均绝对差（MAD），取最小者为真实来源 |
| 4 | **判定**：见下方两条不变量 |
| 5 | **偏差** = `pts_time(匹配到的源帧) − 标称时间 k/R` |

### 第 1 步为什么必须 passthrough

默认解码会对 VFR 素材**补帧凑 CFR**，本项目实测：

| 素材 | 模式 | 容器帧数 | 默认解码 |
|---|---|---|---|
| `4b0460c4` | CFR | 570 | 570 ✓ |
| `6b2eea34` | **VFR** | 780 | **781 ✗** |
| `dcc871b1` | **VFR** | 750 | **751 ✗** |

补入的那一帧插在文件中段，**使其后所有帧号整体偏移一帧**。
用带偏移的基准去测偏差，测出来的东西没有意义（本项目真踩过：一度得到「走廊→走廊」的自相矛盾证据图）。

### 两条不变量（缺了它们，测出的数字不是证据）

| 不变量 | 含义 | 不成立说明什么 |
|---|---|---|
| **匹配 MAD 必须为 0** | 每个输出帧在源里**唯一**对应一帧 | MAD 不为 0 → 匹配有歧义（或该滤镜在混合帧，如 `tblend`），偏差数字不可信 |
| **源帧号必须严格递增** | 输出帧顺序 = 源时间顺序 | 不递增 → 发生了别名（把两个输出帧匹配到同一源帧） |

脚本对这两条都做断言，并在 `--selftest` 里失败即判 FAIL。

## 3. 实测结果

```
$ .venv/Scripts/python.exe measure_sampling_bias.py --selftest

  4b0460c4… 输出  76 帧  MAD max=0.0000 严格递增=True  偏差 min=+0.0993 max=+0.1160 mean=+0.1077
  6b2eea34… 输出 104 帧  MAD max=0.0000 严格递增=True  偏差 min=+0.0954 max=+0.1130 mean=+0.1041
  dcc871b1… 输出 100 帧  MAD max=0.0000 严格递增=True  偏差 min=+0.0927 max=+0.1217 mean=+0.1079

  [PASS] 三段偏差同号且一致（均值 +0.1066s） → 系统性偏差，不是随机抖动
```

**三条结论：**

1. **偏差恒为正**（+0.09 … +0.12s），即 `fps=4` 第 k 帧的内容取自源 PTS ≈ **k/4 + 0.105s**，
   比标称晚约 **0.105s ≈ 0.42 个 0.25s 采样格**。
2. **是系统性的**：三段同号、极差仅 0.029s（远小于随机抖动该有的量级）。
3. **与 CFR/VFR 无关**：CFR 的 `a` 段偏差（+0.1077）**最大**，VFR 的 `b` 段（+0.1041）最小。

> 第 3 条纠正了本项目分析报告里的一处说法：原文称 `frames/` 的「帧序号↔时间」换算
> **只对 a(CFR) 精确**。实测**恰恰相反**——该偏差来自 `fps` 滤镜自身，三段同级。
> 若沿用原说法，下游会误信「a 的 4fps 帧更精确」。

### 偏差不是常量（这是最需要说清的一点）

逐帧看偏差序列，它**不是常数，也不是逐帧查表**，而是有确定结构：

| 素材 | 出现过的偏差取值 | 结构 |
|---|---|---|
| `a`（CFR） | **+0.0993 / +0.1160**（仅两个值） | **纯周期 2**，两值相差 **0.0167s = 半帧**，去掉周期后残差 std = **0.00000** |
| `b`（VFR） | +0.0954 / +0.0964 / +0.1120 / +0.1130 | 两个主相位 + 约 0.001s 小漂移 |
| `c`（VFR） | +0.0927 / +0.1050 / +0.1094 / +0.1217 | 丢帧点**前**两相位 {+0.1050, +0.1217}，**后**两相位 {+0.0927, +0.1094}，整体下移 **−0.0123s** |

**成因可以完全解释：**

- **周期 2 的来源**：`30 / 4 = 7.5` 不是整数。待测滤镜必须在 floor 与 ceil 之间取一个源帧，
  于是选中的源帧号以 **7, 8, 7, 8 …** 交替（实测步长分布 `a` = {7:38, 8:37}），
  残差因此以半帧为幅、周期 2 地来回摆。**这与素材无关，只由 R 与源帧率决定。**
- **台阶的来源**：VFR 丢帧使后续帧的真实 PTS 整体后移，采样残差随之平移。
  `a`（CFR）没有任何台阶，偏差**严格只有两个取值**——这正是"不是常量"的最干净证据。

**因此正确的表述是**：偏差 ≈ **+0.108s**（周期项 ±0.008s）+ **丢帧处的小台阶**（c 实测 −0.012s），
总跨度 **+0.093 … +0.122s**。**不要承诺常量，也不需要逐帧查表**——
它由 R 与源帧时序决定，可复现。

> 对本项目而言，0.03s 的总跨度远小于 0.25s 音频时间码分辨率，
> 所以下游统一按「约 +0.10s」修正是安全的；但**表述上不能写成精确常量**。

## 5. 用法

```bash
cd "C:\Users\18930\Desktop\Edit skill"

# 不变量自测（三段素材跑 fps=4）
.venv/Scripts/python.exe projects/game-001/verification/frame-probe/measure_sampling_bias.py --selftest

# 测任意「按时间抽帧」的滤镜
.venv/Scripts/python.exe projects/game-001/verification/frame-probe/measure_sampling_bias.py \
    --input "原始素材/6b2eea343eee7595c3c0ede10d21d028.mp4" --filter "fps=2" --fps 2 \
    --json-out bias-fps2.json

# 测别的工具产出的帧序列？把它的抽帧命令行换成 --filter 即可
```

`--fps` 是**该滤镜的标称输出帧率**（用于算标称时间 k/R），不是源帧率。

## 6. 已知局限（诚实声明）

1. **依赖「帧内容可唯一匹配」。** 若源里存在**完全相同的连续帧**，多个源帧会得到 MAD=0，
   而脚本在并列时取**较小下标**，会把偏差向负方向低估。本批素材运动量大
   （相邻帧差中位数 8.3–9.3 / 255），且跳变点附近的相邻帧差也在 0.09–0.17（非严格 0），
   故不构成实际影响；但**换到静态素材就要警惕**，`source_index_strictly_increasing` 只能
   抓住"整体别名"，抓不住单帧并列。
2. **只适用于"每输出帧选一个源帧"的滤镜**（`fps`、`select`）。对会混合帧的滤镜
   （`tblend`、`minterpolate`）MAD 不会为 0，脚本会以不变量失败**响亮地**报出来——这是期望行为。
3. **测的是"标称时间约定"，不只是滤镜行为。** 脚本假定输出第 k 帧的标称时间是 `k/R`（从 0 起算）。
   若某工具用别的锚点（例如从首帧 PTS 起算），测出的偏差会**同时包含**该锚点约定。
   这其实正是我们要暴露的东西——「声称 = k/R」本身就是要被检验的命题。
4. **窗口 14 帧、降采样 4 倍**是针对本批素材（30fps、720p）选的。换素材若出现 MAD≠0，
   应先放大窗口重测，而不是直接采信数字。
5. **不判断哪一帧"应该"被选中。** 本工具只报告实际选中了什么；是否合理属于剪辑判断。
