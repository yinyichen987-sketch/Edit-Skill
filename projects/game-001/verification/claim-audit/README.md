# claim-audit —— 「规格声称 ↔ 脚本实现」一致性审计器

防的失败模式：**规则写在规格里、声称在文档里、排除在脚本外**，于是三个脚本全绿而规格是假的。

- 脚本：`audit_claims.py`（自带反例自测）
- 结果：`claims.json`
- 生成日期：2026-09-12 ｜ 作者：creative-reviewer

---

## 1. 为什么需要它

本项目实测到过一个**三层齐备的假保证**：

| 层 | 内容 |
|---|---|
| **规则存在** | `format-spec.md:70`「高光前后各留 **≥0.3 s** 余量」 |
| **声称存在** | `format-spec.md:436`「4 个片段的 8 个切点**全部达标**」，并引用了脚本名 |
| **实现不存在** | 被引用的 `_check_cutmargins.py` **文件根本不存在**；`verify_cut_margins.py` 的 **docstring 写了 0.3**，正文只有 `0.10` 与 `0.034`，跑出来仍是 `ALL PASS` |

即：**校验器的声明范围大于它的实现范围，于是「全绿」被当成「已满足」。**

这比单个技术缺陷更危险，因为**它不会让任何东西崩溃**，只会让交付物带着一个
"自己声称已满足、实际未满足"的验收项发出去。分级依据不是"崩不崩溃"，而是**"会不会骗到人"**。

## 2. 判据（两条，均可自动检查）

| # | 判据 | 说明 |
|---|---|---|
| **A** | 规格里任何被引用的脚本**必须真实存在** | 专抓"引用了一个不存在的脚本" |
| **B** | 规格里作为**判据声明**的数值阈值，必须在**某个脚本的可执行代码**里真正出现 | 专抓"只在 docstring/注释里写了阈值，代码没实现" |

### 判据 B 的两个关键设计

**1. 只认"可执行代码"，不认注释与字符串。**
第一版在整份源码里做子串搜索，结果**漏判**了真实缺陷——因为
`verify_cut_margins.py` 的 docstring 里就有 `>= 0.3`，子串搜索因此通过。
改用 `tokenize` 取 **NUMBER token** 后，`0.3` 判为"代码中不存在"，
并额外报告它**只出现在注释/字符串里**。**"文档里提到"不等于"代码里实现"。**

**2. 只认"比较符/量词旁边的数字"当阈值。**
第一版只要同一行出现"余量/容差"就收走该行所有小数，把 `15.00`、`21.40`、`48.96`
这类**描述性数据**也当成阈值，一口气报出 **40+ 条**。
**一个"什么都要报"的检查等于没有检查。** 现在只匹配三种形态：`≥0.3`、`0.3 s 余量`、`留 0.034`。

**3. 实现搜索是全仓的，不限于"本文档引用的脚本"。**
只查被引脚本会把 CAP-03 的 `1.2` 也误报——它其实由 `verify_t4_deliverables.py` 实现，
只是规格文档没引用那个脚本。**误报和分析漏洞一样糟。**

**5. 自测不能绑定"被检对象的当前状态"。**
第一版自测断言"本项目当前存在 `_check_cutmargins.py` 失效引用与 `0.3` 未实现"。
t4 真的把 `0.3` 实现进脚本后，**自测立刻转为 FAIL**——它把"检测器能工作"和"项目有缺陷"
绑在了一起。两个害处：① 项目一改善它就变红，看起来像工具坏了；
② 更糟，它**诱使人为了让自测变绿去保留缺陷**。
现改为**合成夹具**：当场造一个"只在 docstring 提到 0.3 的脚本 + 引用了不存在脚本的文档"，
断言两条都被抓出；**并加了反例**——把 0.3 真正写进代码后，断言不再报 0.3（证明它会收敛）。

**6. 文档"诚实地记录自己已修的错误"不应被惩罚。**
t4 修好后，`format-spec.md:440` 写「旧文…引用了**不存在**的脚本 `tools/_check_cutmargins.py`…已删去该引用」。
第一版把这个**记录错误本身**的句子当成失效引用报 FAIL。
现判据：某一引用的**所有**出现处都带"历史/更正"语义词（不存在/已删/已更正/失实/旧文…）时，
降级为 `[info]`，不计入 verdict。
> 局限：这是个启发式，理论上可以用一句"不存在"把真引用洗白。
> 所以报告里把它单列成 `historical_mentions` 段，**仍打印出来给人看**，只是不阻塞。
两个方向各修一次：
- **漏洞方向**：第一版哪怕带 `--run`，verdict 也只看"是否实现了"、**不看运行结果**。
  于是存在一个洞：**只要"实现了"这条判据，哪怕实现它的脚本一跑就失败，门禁也会转绿**——
  "有脚本"被当成了"判据被满足"。这正是本工具要防的那类错误，不能在自己身上再犯。
- **误报方向**：把退出码计入后，`analyze_film.py` / `edl_to_draft.py` 也被算作失败——
  但它们是被文档当作**命令行工具**提到的，裸跑必然以 usage 错误退出（exit=2）。
  因为"没给它参数"而判交付物失败，是典型的假阳性。
  现在只有**被"声称"引用**的脚本计入 verdict（标注 `[门禁]`），其余标注 `[仅信息]`。

## 3. 自测（合成夹具 + 反例）

自测用**当场合成的夹具**验证判据 A/B 会触发、且会收敛——**不依赖项目当前状态**：

```
$ .venv/Scripts/python.exe audit_claims.py --selftest
  [PASS] 判据A 抓出「被引用但不存在的脚本」: ['tools/does_not_exist.py']
  [PASS] 判据B 抓出「阈值只在注释/字符串里」: [('0.3', ['tools\prose_only.py'])]
  [PASS] 判据B 反例：阈值进了代码后不再报 0.3
```

> 夹具：一个只在 docstring 里写 `>= 0.3`、代码里只有 `0.10`/`0.034` 的脚本；
> 一个引用了它的文档；以及一条引用不存在脚本的句子。
> 第三条断言是**反例**：把 `0.3` 真正写进代码后，判据 B 必须**不再报**它。

**A. 被引用但不存在的脚本**
```

```

**B. 声明为判据、但全仓任何脚本的可执行代码里都未实现的阈值**（全部是 `0.3`）
| 位置 | 语境 |
|---|---|
| `format-spec.md:70` | 「切点精度上限是 ±0.1 s（CUT-05）。高光前后各留 ≥0.3 s 余量」 |
| `format-spec.md:432` | 硬约束表第 2 条 |
| `episode-plan.md:28` | 新增约束 |
| `episode-plan.md:57` | 「以 CUT-05 留 ≥0.1s 容差 + 高光前后 ≥0.3s 余量」 |
| `episode-plan.md:141` | 反例表 CUT-05 |

全部只有 `verify_cut_margins.py` 的**注释**里提到 `0.3`，
**没有任何脚本的可执行代码实现它**。

**C. 附带发现——规格在描述校验脚本时"漏列"了这条规则**
`format-spec.md:383`：
> `verify_cut_margins.py`：CUT-04 上界余量 + CUT-05 切点距跳变/丢帧 ≥0.1s + 零间隙 + 总长 → **ALL PASS**

这行**逐项列举了该脚本检查什么，却没有 `≥0.3s`**——等于文档**自己承认**了这条规则不在校验范围内；
而同一文档第 436 行又写「8 个切点**全部达标**」。**同一份规格前后不一致**，这是比违规本身更根本的问题。

**D. 另一处"无脚本支撑的声称"**
`episode-plan.md:154`：「旧方案违规 2 处，新方案违规 **0 处**（脚本判定 `RESULT: ALL PASS`）」——
该行**没有点名任何脚本**（`cited=[]`，只笼统说"脚本判定"）。声称"0 违规"却不指向
**哪一份**判据实现，因此不可复现。

## 5. 用法

```bash
cd "C:\Users\18930\Desktop\Edit skill"

# 反例自测（必须报出本项目两个已确证缺陷）
.venv/Scripts/python.exe projects/game-001/verification/claim-audit/audit_claims.py --selftest

# 门禁模式（**要求 exit=0 时必须用这个**）
.venv/Scripts/python.exe projects/game-001/verification/claim-audit/audit_claims.py --run \
    --json-out projects/game-001/verification/claim-audit/claims.json

# 静态模式（只查引用存在性与阈值实现，不运行被引脚本；快，但会漏掉"存在却失败"）
.venv/Scripts/python.exe projects/game-001/verification/claim-audit/audit_claims.py
```

> ⚠️ **要求 exit=0 当门禁时，必须带 `--run`。**
> 不带 `--run` 时，只要 t4 把 `≥0.3s` 写进某个脚本、哪怕那个脚本一跑就报失败，
> 本工具也会转绿——因为它只检查"有没有脚本实现"，不检查"脚本运行是否通过"。
> 另一个轴（EDL 是否真的满足 0.3s）由 `../run_t5_checks.py` 的审阅侧实现独立判定。

退出码：`0` = PASS，`1` = FAIL。`--run` 会执行被引用的脚本，**只对可信脚本使用**。

## 6. 已知局限（诚实声明）

1. **判据 B 只证明"阈值出现过"，不证明判据逻辑正确。** 它专抓"声称里有 0.3、
   代码里根本没有 0.3"这类**完全没有实现**的情况；一个写错比较方向但含正确字面量的脚本仍会通过。
2. **阈值提取是形态匹配**，只认 `≥x` / `x 余量` / `留 x` 三种写法。
   规格若把阈值写成自然语言（"三成左右的余量"）就抓不到。
3. **`--run` 会执行被引用的脚本**，可能写文件。默认关闭。
   **门禁模式必须开 `--run`**（否则"存在却失败"的脚本会骗过它），并只对可信脚本使用。
4. **只扫 `spec/` 下两份文档**（`--docs` 可覆盖）。主报告 `analysis/summary.md`、
   `research/*.md` 里的声称尚未纳入。
5. **"声称"是靠关键词识别的**（达标/已满足/无违规/ALL PASS…），换措辞可能漏识别。
   这是**漏报**方向的风险，比误报安全，但需要人留意新表述。
