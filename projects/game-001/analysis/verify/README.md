# verify/ —— 时间码命名的复核帧

这个目录是给人（和下游 agent）**独立复核时间码**用的。设计目标只有一个：
把「帧号 ÷ 帧率」这种**不可复现**的换算，换成**文件名带时间码的实物**。

任何人拿到一张图，看文件名就知道它对应素材的哪一秒；不需要知道抽帧参数、不需要重算帧率、
也不受 b、c 是 VFR 的影响。

---

## 命名规则

```
<clip>_<highlight_id>_<kind>_<time>s.jpg
```

| 段 | 含义 | 取值 |
|---|---|---|
| `clip` | 素材代号 | `a` = 4b0460c4…、`b` = 6b2eea34…、`c` = dcc871b1… |
| `highlight_id` | 高光编号 | 与 `material-analysis.json` 中 `highlights[].id` 一一对应 |
| `kind` | 帧的取样类型 | `s` / `m` / `pk`（见下） |
| `time` | **该帧在素材中的时间（秒）** | 与报告中的时间码同一基准 |

### 三种 `kind` 的区别（这点很重要，别混用）

| kind | 含义 | 用途 |
|---|---|---|
| `s` | 高光区间的**起点** | 复核「我说这里开始」——看这一帧有没有进入该事件 |
| `m` | 区间的**算术中点** | 只代表区间几何中心，**不代表事件发生点** |
| `pk` | 区间内的**音频能量峰值点** | 复核「我说这里有能量爆发」——最接近事件发生时刻 |

> ⚠️ `m` 是纯几何中点，**不要**把它当作事件时刻引用。
> 要引用事件发生的瞬间，请用 `pk`。

### 特例

```
_gapcheck_b_11.20s.jpg
_gapcheck_c_14.50s.jpg
```
这两个不是高光帧，而是 **VFR 丢帧点之后的对照帧**：
- b 在 **10.979688s** 丢 1 帧 → 取 11.20s 对照
- c 在 **13.971680s** 丢 1 帧 → 取 14.50s 对照

用途：证明「跨过丢帧点之后，帧内容与时间码仍然对齐」。若有人怀疑 VFR 导致时间码漂移，
看这两张即可——它们的内容与报告记录一致
（实测：b 11.20s 为 B区建筑内部、满血 100、Vandal 10/39、比分 0-0；
c 14.50s 为倒计时 1:25、血 50、比分 4-2，画面中弹匣/爆能器标记齐备）。

## 复查方法（可复制执行）

### 方法一：直接看（最常用）
打开任意 `*.jpg`，比对 HUD 上的**不变量**与报告记录是否一致。

### 方法二：自己重新抽同一时刻，与目录里的图对比
```powershell
$ff = ".venv\Lib\site-packages\imageio_ffmpeg\binaries\ffmpeg-win-x86_64-v7.1.exe"
# 例：复核 a 段 6.65s
& $ff -v error -ss 6.65 -i "原始素材\4b0460c400bbb5320acb6063b4f59358.mp4" -frames:v 1 -q:v 2 -y "$env:TEMP\check.jpg"
```
两张图应当**逐像素级一致**（同一时间点、同一解码路径）。不一致说明时间码或素材被改动过。

### 方法三：重新生成整个目录
```powershell
.venv\Scripts\python.exe projects\game-001\analysis\tools\sample_frames.py    # s / m 帧
.venv\Scripts\python.exe projects\game-001\analysis\tools\add_peak_frames.py # pk 帧
```

## HUD 不变量（复核时优先看这几个）

VALORANT 的 HUD 里有若干**数值型**字段，是本批素材最可靠的不变量 —— 它们可读、离散、且随时间单调，
比"画面看起来像什么"可靠得多。建议按下列顺序核对：

| 字段 | 位置 | 为什么好用 |
|---|---|---|
| 倒计时 | 画面顶部中央 | 逐秒递减，是最强的时序锚点 |
| 比分（我方击杀 / 敌方击杀） | 顶部中央两侧 | 跨段可比，能区分不同回合 |
| 血量 / 护甲 | 左下 | 离散值，临界值（2 HP、1 HP）极有辨识度 |
| 弹匣 / 备弹 | 右下 | 每次开火递减，可判断"是否刚开过枪" |
| 击杀播报 | 右上 | 有则=确证发生击杀，是最硬的证据 |

## 已知限制（诚实声明）

1. **`pk` 帧不保证落在其所属高光的区间内 —— 这是系统性倾向，不是个别情况。**
   `pk` 取自 250ms 音频窗的起点，且相邻窗合并为事件段后取段起点，因此时间精度为 **±0.25s 量级**，不是帧级。
   **实测（`tools/audit_verify_dir.py` 全量扫描）：24 个有 `pk` 的高光中，有 6 个的 `pk` 落在自己区间之外，
   且全部朝同一方向（早于区间起点）。**

   | 高光 | 区间 | pk | 偏移 |
   |---|---|---|---|
   | A-H3 | 6.35–6.95 | 4.75 | **−1.60s** |
   | C-H4 | 4.40–5.00 | 3.25 | **−1.15s** |
   | **A-H5** | 11.60–12.20 | **11.25** | **−0.35s** ⚠️ **超出本项声称的 ±0.25s 精度** |
   | A-H2 | 5.00–6.00 | 4.75 | −0.25s（在精度内）|
   | A-H4 | 8.40–9.00 | 8.25 | −0.15s（在精度内）|
   | B-H6 | 23.40–24.00 | 23.25 | −0.15s（在精度内）|

   **机制**：音频能量爆发往往**先于**我从画面确认到的那个状态帧。
   典型是 A-H3 —— 区间是 **6.35s 的临界血量状态帧**（仅 0.6s 长），
   而对应的能量爆发实际发生在 **4.75s**（弹匣倾泻），相隔 1.6s。

   **引用注意**：`pk` 帧用于「这里有能量爆发」，**不等价于「此高光的事件时刻」**。
   越界幅度大的（A-H3、C-H4、A-H5）请按跨区间能量归属理解。
2. **除两处 `pk` 共用外，还有一处 `m` 帧被共用 —— 且后者更危险。** 实测共三处：

   | 类型 | 时刻 | 涉及高光 | 说明 |
   |---|---|---|---|
   | pk | `a` @ **4.75s** | A-H2, A-H3 | 能量证据**跨区间共享**，不能当两个独立事件 |
   | pk | `c` @ **3.25s** | C-H3, C-H4 | 同一能量段的相邻切片（C-H3 承伤、C-H4 过渡）|
   | **m** | `b` @ **23.70s** | **B-H6, B-H7** | **两个高光的中点是同一张图** |

   ⚠️ **`m` 被共用比 `pk` 被共用更危险**：`B-H6` [23.40, 24.00] **完整包含于** `B-H7` [21.40, 26.00]，
   两者中点恰好都算出 23.70s，于是 `b_B-H6_m_23.70s.jpg` 与 `b_B-H7_m_23.70s.jpg` **是同一时刻的同一画面**。
   后果：**若把 B-H6 与 B-H7 当作两个独立高光去选材，同一段 0.60s 画面会被用两次。**
   （A 段与 C 段不存在区间包含关系，只有 B 段这一处。）
3. **`b_B-H4`（13.8s，疑似技能/安放特效）没有 `pk` 帧。** 该区间内没有显著的音频瞬态事件，
   我不生成假的峰值帧 —— 没有能量证据就不假装有。**它是唯一无 `pk` 的高光**（25 个高光中）。
4. **`m` 帧只是几何中点**，见上文警告。且如上所述，**B 段有两个高光共享同一张 `m`**。
5. 本目录**不包含** `frames/` 里的 4fps 连续抽帧。那批帧**不可用于精确时间查询**：
   实测 `-vf fps=4` 的输出帧内容是**就近取样**，其真实内容时刻相对标称 `k/4`
   **系统性滞后约 +0.108s**（a +0.1076 / b +0.1041 / c +0.1079；总跨度 +0.093…+0.122s，恒为正）。
   **该偏差来自 `fps` 滤镜本身，三段一致，与 CFR/VFR 无关** —— 不要以为 CFR 的 a 段就更精确。
   需要精确时间请用本目录的帧或直接按时间 seek。

   > **该偏差不是常量，但有确定结构（无需逐帧查表）**：
   > ① **周期项** —— `30/4 = 7.5` 非整数，滤镜在 floor/ceil 间交替取源帧（步长 7,8,7,8…），
   >    残差以**半帧 0.0167s 为幅**摆动 → 基准 **+0.108s ± 0.008s**；
   > ② **丢帧台阶** —— VFR 丢帧使其后真实 PTS 整体后移，c 段实测下移约 **−0.012s**，
   >    台阶正出现在该段唯一处丢帧（PTS 13.971680）附近。
   > a 段是 CFR 且无丢帧，故其偏差**严格只有两个取值** {+0.0993, +0.1160}。
   > 另需区分：`fps=4` 的**输出时间戳本身严格等于 j/4（实测偏差 0.0000）**，时间轴是线性的；
   > 偏差在于**输出帧的内容取自哪个源帧**。
   >
   > 该结构先由 creative-reviewer 测出，我用 `tools/fps_offset_selfconsistent.py` 独立复核，逐位吻合。
   > **测量陷阱**：像素与 PTS 必须取自**同一次解码**。我第一版工具把像素经 raw 文件解码（b→781、c→751 帧）
   > 却用 showinfo 的 PTS（b→780、c→750）按下标配对，差 1 帧即造成整段下标偏移，均值偏高约 +0.019s。
   > 自证判据：步长分布只能出现 7/8，且偏差取值为 2–4 个离散值。

6. **复核时间码时，比较的图必须同编码。** 本目录是 JPEG。若你用自己的 PNG 帧与目录里的 JPEG 比，
   你会得到 MAD 2.2–3.8 —— 那是**编码差异，不是时间戳错位**。
   正确做法是做**时间码偏移扫描**（−0.10 → +0.10s，步长 1/30s），最优解应出现在 **偏移 0.0000 且 MAD 0.00**。
   （此结论由 creative-reviewer 独立验证：对 5 张帧扫描后，5/5 都在标称时间码处逐像素一致。）
7. 所有时间码基准 = **从媒体起点起算的时间线位置（秒）**，与 ffmpeg `pts_time` 同基准；
   首帧 PTS 非零（a 0.016016 / b 0.013021 / c 0.005013）。详见报告 §2.2。

> **一致性由脚本全量扫描 + 双向断言，不靠人工核对**：
> `projects/game-001/analysis/tools/audit_verify_dir.py` 检查五项 ——
> s/m 时间是否与 JSON 吻合、pk 是否落在区间内、哪些帧被共用、区间包含关系、清单计数。
>
> 它**不设阈值**（"越界个数 ≤ N"这种判据需要人拍一个任意数，而且管不住真正的问题）。
> 判据是**双向断言**：脚本维护一份**已披露异常清单**，然后要求
> **扫出的每个异常都必须在清单里**（防漏披露）**且清单里每条都必须真实存在**（防幽灵披露）。
> 因此「有异常」不算失败，**「有异常却没写出来」才算失败**。
>
> 当前结果：s/m **50 张零不符**；pk 越界 **6/24**；共用帧 **3 处**；区间包含 **1 处** —— 全部已披露，断言通过。
> 可用 `--selftest` 验证断言本身有效（注入假异常，确认漏披露与幽灵披露两个方向都会失败）。
>
> **退出码语义（已分离）**：`0` = 通过 ｜ `1` = 发现漏披露/幽灵披露/硬伤 ｜ `2` = 用法错误。
> 之所以要专门说明：本脚本原先在 **Windows GBK 控制台**下会因打印 `⊂` 抛 `UnicodeEncodeError`，
> 而**崩溃的退出码(1)与审计失败的退出码(1)相同** —— 于是「崩溃」会被误读成「检查未通过」，
> 反之亦然。**一个门禁的两种结论被压成同一个码，等于这个门禁不可读。**
> 现已用 `errors="replace"` 让编码异常路径**彻底不存在**，使 `1` 只可能来自真实结论。
>
> **第 3 类检查（执行环境覆盖）：本门禁已在以下消费环境下逐一验证，全部 exit=0 且无编码错误** ——
> ① 终端直出；② 管道给另一进程；③ 重定向到文件（无 tty）；④ 确定性 BrokenPipe（消费者只读 1 行即关闭）；
> ⑤ 作为子进程被 Python 捕获（且 `PYTHONIOENCODING`/`PYTHONUTF8` 被显式从 environ 删除）。
> **注意**：验证时必须在**默认环境**下进行 —— 设了 `PYTHONIOENCODING=utf-8` 再测，只能说明那个 shell 里成立。
