## 第 1 轮 · 2026-09-12 · 立项与兼容性验证

**本轮目标**：确认 pyJianYingDraft 能否驱动本机剪映 11.4.2，决定整体架构。

**结论**：写路径可用，读路径不可用，架构按「生成草稿 + 人工导出」定型。

### 方法层经验

**1. 先做兼容性验证，再写任何 SKILL.md**

整个方案的形态取决于「自动化库能否驱动目标软件版本」这一个未知数。这一步花几小时，
能省掉几天白工。当时拿到了一份 19 节的训练方案，写得系统，但全篇没验证过工具链，
也没提剪映——如果照着写规则和评测集，大概率全部作废。

> 下次：任何「让 agent 操作某个桌面软件」的项目，第一步永远是端到端最小验证。

**2. 不要用「手写 SOP」当训练数据**

原本计划让用户手写 shot-by-shot decision log 来提炼风格。这很低效，因为训练信号质量
取决于用户的文字表达能力，而不是真实剪辑手法。更好的信号源是**机器可读的决策记录**。

> 下次：优先找「操作痕迹本身就是结构化数据」的信号源，而不是让人转述。

**3. 上游的合规立场要当成硬约束，不要试图绕**

pyJianYingDraft 明确不内置解密。虽然社区有解密工具，但那是绕过商业软件的技术保护措施，
且软件升级即失效。选择改走「分析成片」路线——信息量略少，但合法、稳定、不怕升级。

> 下次：遇到「上游刻意不做」的功能，先读它的 release notes 看理由，再决定是否绕。

### 技术层踩坑（都是实测出来的）

**4. `pyJianYingDraft.time_util.tim()` 对裸数字按微秒解释**

```python
tim(0.5)     # -> 0        ← 0.5 微秒取整为 0
tim("0.5s")  # -> 500000   ← 正确
```

后果：生成出**时长 3 微秒**的视频片段，草稿表面正常、打开才发现全错。
所有时间必须写成 `f"{seconds}s"`。

> 已固化：`references/edl-schema.md` 已知陷阱 §1

**5. 转场必须在入轨前挂好，否则静默丢失**

`ScriptFile.add_segment()` 只在**入轨那一刻**把 `segment.transition` 登记进
`materials.transitions`。先入轨、之后再给前序片段补转场 → `transitions: []` 全空。

正确顺序：**构造全部片段 → 挂转场 → 统一入轨**。

> 已固化：`references/edl-schema.md` 已知陷阱 §2

**6. ffmpeg `scdet` 以亮度差为主，等亮度换色会漏判**

实测深蓝→深红硬切只有 **5.47** 分，亮暗差异明显的切点有 **23.05** 分。
默认阈值 10 直接漏掉前者。**固定阈值不可靠**。

对策：`threshold=0` 全量采样 + 自适应基线（中位数+标准差）峰值检测。

> 已固化：`references/environment.md` 限制三

**7. 生成的草稿文件比原生少不影响使用**

pyJianYingDraft 只生成 2 个文件，剪映原生草稿有 24+ 个条目。一度担心剪映不认，
实测**可以正常识别**，缺失文件由剪映首次保存时自行补齐。

> 教训：不要凭文件数量差异就假设不兼容，实测比推断可靠。

### 流程层经验

**8. 有些验证只有人能完成，必须显式设计人工环节**

「剪映能否打开这个草稿」无法自动化（剪映 7+ 也没有自动导出）。这类环节要在流程里
明确标出来，而不是假装端到端自动化了。

**9. 写测试夹具时，夹具本身可能掩盖问题**

最初的测试视频是连续动画，没有镜头切换，导致切点检测「看起来正常」。造了带硬切的
夹具后才暴露出低分切点漏判。**夹具要有能触发边界情况的构造**。

### 交付层经验（本轮新增的一类）

**10. ★ 交付包必须做「往返验证」—— 否则不知道自己交出去的是个打不上 / 打不对的包**

朋友的仓库我没有推送权限，所以本轮第一次走「打补丁交接」：
`git format-patch fef3f9e..HEAD` → 在一个从 `fef3f9e` 起的**临时仓库**里 `git am` → **比 tree**。

> 比 tree 而不是比 commit hash：`am` 出来的提交 committer/时间不同，hash 必然不同，
> **tree 相等才等于「内容一致」**。

第一次跑的结论是 **tree 不一致**：3 个 JSON 的 blob 差 **「行数−1」个字节** ——
本地是 **CRLF**、补丁打出来是 LF。
根因：`pathlib.write_text(..., encoding="utf-8")` 在 Windows 上默认 `newline=None`，
会把 `\n` **翻译成 `\r\n`**。全仓库 763 个文件里恰好只有这 3 个是 CRLF，
**全是第 8/9 轮用 Python 写出来的 JSON**。

修法：`write_text(..., newline="\n")`；并把那 3 个文件归一化为 LF（提交 `47ef417`）。
修完再跑一次往返验证：**tree 完全一致（`020ac170…`，3 个提交，`am exit=0`）**。

⇒ 两条可复用结论：

- **交付动作要自己先验一遍**：补丁能否干净应用 + 打完的 tree 是否等于本地 tree。
- **Python 在 Windows 上写文本文件，换行必须显式指定**，否则默认给你 CRLF。
  这和第 8 轮「`tar.exe` 解不了中文路径」是同一类坑：**跨工具链的默认值不能想当然。**

**交付物位置**（本轮生成，不入库）：`%TEMP%\edit-skill-delivery\`
—— `round8-9-kill-frame-training.patch`（3 个提交，259 KB）+ `kill-frame-training-round8-9.bundle`（42 KB，含前置 `fef3f9e`）。

## 第 2 轮 · 2026-09-12 · 游戏视频第一集（VALORANT，抖音/B站双版本）

**本轮目标**：用 3 段共 70 秒的 VALORANT 原素材，产出面向自媒体涨粉的剪辑形式与成片草稿。

**结论**：交付 1 集 × 2 版本（LS 1920x1080 → B站；VT 1080x1920 → 抖音），
15.00s，两份剪映草稿，规格 + 风格规则集 + 4 个验证工具。门禁 10/10 PASS（默认环境 exit=0），
独立审阅 verdict=pass。**但代价极大**：验证基础设施从 1 个工具长到 4 个，耗时远超预期。

### 本轮最重要的产出不是视频，是一套「错误分类学」

本轮撞到 **11 次「表面正常、结果错误」**的静默失败。团队把它们归纳成 6 类 + 1 条反向规则
（`projects/game-001/analysis/material-analysis.json` 的 `artifact_index.error_taxonomy`）：

| # | 类别 | 实例 |
|---|---|---|
| 1 | **证据覆盖 < 结论范围** | 抽 1/8 帧就断言"素材无硬切"；验一处 HUD 就推广到四处 |
| 2 | **工具可信度 < 结论可信度** | 测量工具自身索引错位，还把结果当真值复用一轮 |
| 3 | **执行环境覆盖不够** | 门禁 exit 码依赖 `PYTHONIOENCODING`；崩溃码与失败码同为 1 |
| 4 | **测量方式覆盖不够** | `cmd \| findstr` 把末命令的退出码当被测程序的 |
| 5 | **产物缺陷被下游继承** | 我的转述把 t1 的结论加工后传给 t3 |
| 6 | **修正覆盖面 < 错误散布面** | 同一句错误散落多处，只改了记得的位置 |
| — | *反向规则* | **不要无证据地揽责——与推卸责任同样会埋掉真因** |

**共同检查动作**：把结论写成"已验证"之前问 *我的验证覆盖了哪些情况？哪些没覆盖？*
第三类再加 *换个环境/调用方还成立吗？*

> **第 3 类的第三个面：时间维度（本轮新发现）**
> 原本"执行环境覆盖不够"指的是「同一脚本在不同环境给出不同结论」；本轮补上「**同一磁盘在不同时刻被不同的人读到**」。
> 本轮我与 `footage-analyst` 并发编辑同一批文件，双方各自读到对方的中间态并互相"更正"，
> 而 `creative-reviewer` 也多次基于过期快照给结论——**它自己靠"以磁盘为准再跑一遍"逐个消除了**。
>
> 两条配套的纪律：**引用数值必须给出源（文件:行）**解决"读者能否判断这是不是现值"；
> **重跑**解决"双方是否在看同一个状态"。缺任一条，就会出现双方各自更正对方。
>
> `footage-analyst` 还指出一个有用的不对称：**四类"空间切法"里只有「对象子集」能在同一份产物内被自己发现**
> （数据都在手上），另三类都必须靠跨文件/跨形态搜索才暴露——这解释了为什么"VT 验了、LS 没验"能被单跑一个脚本抓到，
> 而"同一句错误散落在 §4.1 与 §4.2"必须做全量 grep 才捞得出。

### 方法层经验（本轮新增，按价值排序）

**1. 任何"已完成/已覆盖/已导致"的语句，都要附上它的证据边界**
三条独立教训收成同一条规则：**结论**要声明覆盖范围；**修正**要声明覆盖范围（改了哪几处、有没有全量搜索）；
**因果/传播主张**要声明证据。"只有一处错"必须说清扫的是什么形态。

**2. 「没有证据表明 P」≠「有证据表明非 P」**
前者是证据缺失，后者是正向证据。审阅时应当去扫一遍把前者升级成后者。

**3. 未被覆盖的轴应当被声明为未被覆盖，而不是留白让人以为已覆盖**
本轮的"规格换算时间码 ↔ EDL 实际时间线"没有任何自动化覆盖，靠人工全量复算兜住——**并把它写进 §13**。
另外：「我们知道我们没测这个」**无需外部证据**即可完成，因此没有借口不做。

**4. 一条决定通过/失败的规则，必须指明它作用在哪个量上**
本轮同一缺口出现三次：`≥0.3s 余量`是相对**区间**还是**起点**；`CAP-04` 比的是**起始间隔**还是**时长**；
`1620` 是**字形**还是**中心**上限。

**5. 把规则口径降到可测量的量，再用位置吸收不确定性**
判据从"字形外框"降为"文本框中心"（因为剪映无公开 `size→px` 换算，比例还不自洽），
**同时把落点放到离禁区足够远处，使结论对两种口径都成立**。
> 用位置的选择吸收口径的不确定性，而不是用口径的模糊掩饰位置。

**6. 「理由错而结论对」也要改理由——否则错理由会以正确结论的名义传播**
推论：**修正也要声明覆盖范围**，且应**按「句子」搜，不按「缺陷」搜**——
同一句话可能有多个副本，按缺陷修会"两处都改过、但都漏了第三处"。

**7. 审查工具本身必须先被验证**
> 一个永远返回 0 的审计脚本，和一个真的在检查的审计脚本，对外表现完全一样。

- 必须做**正例 + 反例**双向控制：**反例证明不漏报，正例证明不误报**，缺一工具的可信度都是假的
- 自测**不能绑定被测对象的当前状态**（否则会"诱使人为了自测变绿而保留缺陷"）
- **误报和分析漏洞一样糟**；"什么都要报"的检查等于没有检查

**8. 被审方的判据不能由被审方定义；执行层不能审自己**
两层独立性：`draft-audit`（草稿是否真的等于 EDL，不由生成器自证）+
固定基准 vs 读规格比对（规格改阈值会被报出而不会自动放宽）。

**9. 不要无证据地揽责**
「即便不是直接原因，也是同一类污染源」这类措辞**自带免责却完成了归因**，比直接断言更难发现——
因为它已经预设了自己不武断。害处有三：让下一个人查错方向、把真教训埋在错误标题下、
给团队"已经有人认了"的错觉从而**降低深挖真因的动力**。

**10. 冲突不能当作"不判定"的理由**
本轮有个真违规长期以 "OPEN ISSUE" 的名义挂在通过态里，理由正是"规格内部两处冲突"。
**规格内部矛盾本身是应当解决的缺陷，不是不判定的许可证。**

### 技术层踩坑（新增）

**11. 剪映草稿 JSON 的三个反直觉结构**（已固化进 `references/environment.md`）
没有 `segment.transition` 字段（转场在 `extra_material_refs` → `materials.transitions[]`）；
文字在 `materials.texts[id].content` 且是**再套一层的 JSON 字符串**；
转场挂在**前序**片段（映射 `segments[j] ↔ clips[j+1]`，非同下标）。

**12. 转场是"重叠"不是"额外占时"**
按后者建模会在片段间留出没有素材的空隙 → **每处转场闪黑**。自检口径：**若 `Σ duration < end`，就一定有黑洞。**

**13. 素材不一定是 CFR；默认解码会为 VFR 补帧凑 CFR**
补入的帧在文件中段，**其后帧号整体偏移 1**，导致时间戳差一帧。判据必须对账"解码帧数 vs 容器帧数"。

**14. Windows GBK 控制台陷阱（环境级，不是个别脚本疏漏）**
打印 `⊂`、`−` 等字符会抛 `UnicodeEncodeError`，而且**崩溃退出码与"检查未通过"的退出码都是 1**：
崩溃会被读成"审计未通过"，"审计未通过"也可能被读成崩溃——**两个方向都会误判**。
约定：所有 CLI 脚本 `main()` 开头 `sys.stdout/stderr.reconfigure(encoding="utf-8", errors="replace")`，
**退出码语义显式分离（0=通过 / 1=审计发现异常 / 2=用法错误）**，并全量检查同类脚本。

**15. 字幕落点与平台 UI**
抖音底部约 300px 被 UI 覆盖（VT 中心上限 1620）；顶部遮挡**未建模**，需人工用抖音预览确认。
横屏版字幕只能叠在游戏画面上，竖屏版有 68.3% 的可控设计区——**这是两版设计上的真正差异点**。

### 流程层经验（Agent Teams）

**16. 运行中的团队无法再修订计划**（`edit_plan` 返回 "team is already running"）
→ **技术约束必须在 staged 阶段写足**；开工后只能靠消息补，而消息不落在任务书里、追溯性差。

**17. 契约缺陷连续阻挡 4 次提交**（值得作为交付物级风险）
- verify 命令指向了 deliverables 之外的文件（captain 配置错误）
- 并发重派会撤销成员当回合已 claim 的 attempt → "做完却提交不了"
- 验证器的 `changedPaths` **只认 `inScope` 的目录路径**，不认 deliverables 里的文件路径
  → 绕过办法是传 inScope 目录；否则成员会反复撞 `undeclared`
- `claim_task` 返回的 attempt_id 与 `update_task` 期望的不一致时，成员**做完也无法登记**

**18. 审阅循环要有出口**
本轮 t6→t7(needs_revision)→t8(repair)→t9(pass)。修正 3 次后**必须收口**——
"改到文档措辞完全准确"是无止境的，而交付没有落地。**给 t5/t9 一个可审的终态，比继续改更有价值。**

## 第 3 轮 · 2026-09-13 · 剪映操作知识内化（外部知识卡片 + 第一方实测）

**本轮目标**：把别的 AI 整理的 53 张剪映知识卡片学进来，补上「操作层」知识。

**结论**：卡片只能当**功能清单**用，不能当事实源。真正可信的操作事实全部来自剪映自己的文件。
本轮产出了 `references/operations.md`（操作知识库）+ `scripts/keymap_report.py`（键位核查工具）。

### 方法层经验

**1. 「知识卡片」是学习材料，不是可信源 —— 必须逐条回到第一方**

53 张卡片结构完整（意图/步骤/禁忌/验证/来源），看起来很可依赖。实际核查：

- 它的「证据来源」栏 **基本不可核查**：核心来源 `blog.iflux.art` 域名已解析不了（NXDOMAIN），
  引用它的卡片有 7 张；其余是 B 站付费课程页和抖音客户端内容。
- 实测查出一条**标着 high 置信度的错误**：卡片说「分割 = Ctrl+B」，而 Ctrl+B 只是
  **Final Cut Pro X 方案**下的绑定，另一套内置方案里分割是 Ctrl+K。（见 `operations.md` §6.1）

> 下次：拿到「别人整理好的知识库」时，先抽查它的**证据链能不能走通**，再决定信几分。
> 结构完整 ≠ 内容正确；**confidence 标注是作者的主观，不是验证结果**。

**2. 判断「某功能在这个版本存不存在」，去读软件自己的文件**

本轮验证功能名/键位的三条第一方通路，比搜网页快且硬：

| 想知道 | 去哪读 |
|---|---|
| 功能叫不叫这个名字 | `Resources\po\zh-Hans.po`（界面文案表，1.4 MB） |
| 这个功能存不存在、命令 ID 叫什么 | `VECreator.dll` 里的命令 ID 字符串表 |
| 快捷键到底是什么 | `User Data\Config\Shortcut\*.json` |

一次 grep 就把 20+ 个功能名全部证实了，比几十个网页可靠。

> 下次：**软件本地的资源文件是最高优先级的证据源**，先找它，再考虑上网。

**3. 有些问题本身就问错了，要先修问题**

用户（和卡片）都在问「剪映的快捷键是什么」。这个问题**没有唯一答案**——剪映内置多套键位方案，
同一功能就是不同的键（93 条命令里 18 条冲突）。正确答案不是某个键，而是
「功能名 + 方案名」。**发现前提错误时，交付的是修好的问题，不是硬凑的答案。**

**4. 交叉验证要用独立来源，别用同一篇二手文的转载**

网络核查找到的「Q = 插入剪辑 / W = 覆盖剪辑」是 Premiere 的概念被误搬到剪映上；
而本地键位文件里 `cutLeft/cutRight = Q/W` 在所有 5 套方案里完全一致。
**二手来源之间会互相抄，本地文件不会。**

### 技术层踩坑

**5. 剪映的键位方案是文件，不是注册表**

`…\Config\Shortcut\` 下 5 个 JSON（Custom1/2/3 + Final Cut Pro X + Premiere Pro），
首次运行一次性写入；`Config\keymapSettings` 只有 `currentKeymapIndex=0`，
**「索引→方案名」没有任何可读文件** → 不要推断，去界面确认。
工具：`.venv\Scripts\python.exe .dsh\skills\jianying-edit\scripts\keymap_report.py --compare`

**6. 定格没有默认快捷键**

两套方案里 `storeSingelFrame` 都是空数组。之前如果想「按个键再等等看」，永远等不到。

**7. 联动的默认范围会咬人**

本机 `Config\globalSetting` → `linkageEnableTypes=text, effect, sticker, filter, adjust, sound, tts`。
即**字幕默认在被联动清单里，但效果/贴纸/滤镜也在**——「全选后整体移动」时要想到这些会一起动。

**8. Windows 上 `ConvertFrom-Json` 读剪映的 UTF-8 键位 JSON 会直接失败**

键位值里有全角字符（`Ctrl+；`、`Ctrl+，`），PowerShell 用 ANSI 解码后变成非法 JSON 并报
`Invalid array passed in, ',' expected`。**读这类文件一律走 Python（显式 `encoding="utf-8"`）。**

**9. 别对 `Program Files` 做递归扫描**

一次 `Get-ChildItem -Recurse -Depth 4` 扫三个 Program Files 目录直接 120 秒超时。
**先解析快捷方式的 TargetPath**（`WScript.Shell` COM）就能秒定位安装目录 —— 本轮 5 秒拿到 `E:\JianyingPro`。

### 流程层经验

**10. 网络工具会整片挂掉，委派时要给「替代路径」**

**11. 「每轮必须推送」是硬要求，而本 harness 里推送需要更宽权限**

用户明确要求：**每次训练都要上传到 GitHub**（<https://github.com/yinyichen987-sketch/Edit-Skill>）。
本轮第一次 `sync.ps1` 推送失败，报的是

```
schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030E)
```

**我一开始差点把它当成凭据/网络问题** —— 实际是沙箱限制了 schannel/SSPI 的 TLS 初始化：
默认模式下连 `git ls-remote` 都挂，而代理端口明明是开着的；换成 `danger-full-access` 重跑，
同一条命令立刻成功。已经把这个情况写进 README（退出码 3）和 `environment.md`。

顺带修掉一个**会让诊断永远打不出来**的坑：两个同步脚本开头是 `$ErrorActionPreference='Stop'`，
而 git 把 SSL 错误写到 stderr，用 `2>&1` 捕获时 PowerShell 把它升级成终止性错误，
脚本在诊断代码之前就挂了（实测：补丁打了但不生效）。捕获原生命令输出前必须临时切回 `Continue`。

并且把脚本改成**先提交再推送**：推送被挡时本轮成果仍在本地，不会因为网络/权限丢掉成果。

> 下次：这个环境里所有「像网络问题」的失败，**先怀疑沙箱**（pip 的 %TEMP%、Python 的 TLS、
> git 的 HTTPS 是同一类）。

**12. `edit` 工具会吃掉 .ps1 的 BOM（本轮第二次踩同一个坑）**

`environment.md` 早就写了「含中文的 .ps1 必须带 BOM」，我也确实遵守了——但用 `edit` 工具打补丁后
**BOM 被静默删除**，脚本立刻报一串和 BOM 毫无关系的 `Missing closing '}' in statement block`。
第一反应是「补丁写错了」，查了三轮才发现是编码问题。

> 下次：**凡是改 `tools/*.ps1`，改完立刻复检 BOM 并跑一遍 `Parser::ParseFile`**，
> 别相信肉眼，也别先怀疑逻辑。

## 第 4 轮 · 2026-09-13 · 爬参考成片 + 击杀帧提取的标定校准

**本轮目标**：确认「能不能真的上网搜/爬瓦洛兰特剪辑视频来学模板」，重点是击杀帧提取。

**结论**：能 —— 搜索/下载/分析/**看图**四条链路全部打通。
而一打通就发现：**击杀帧提取的标定一直是错的**，`16.733` 这类"击杀"其实是战术面板弹出。

### 方法层经验

**1. 跑得久的判据，最容易被当成"已验证"的判据**

`tools/detect_kills.py` 的击杀列表进了 EDL、进了成片，看起来"经过这么多轮验证"。
但它**从来没有被目视核对过** —— 全是信号处理自证。第一次把横幅抽出来看一眼，
就发现底部标定截错了位置（只覆盖横幅下缘 14px）。

> 下次：任何"提取/检测"类判据，**上线前必须至少目视核对几条**。
> 管线越顺、下游越多，越容易把上游的错误固化。**信号自证不算验证。**

**2. 一个判据换个场景，会悄悄改变语义**

「底部特效 ∩ 右上播报（±0.8s 共现）」在**未剪辑素材**上是击杀判据；
到了**已剪辑成片**上，因为硬切会让整帧同时变化，它**退化成切点探测器**
（`BV19m3uzhECJ` 6 个候选 **6 个全落在切点 ±0.25s 内**）。

更危险的是它**产出了一个漂亮的假规律**：我算出"击杀后中位 0.03s 就切走"，
看着非常像行业手法 —— 实际是"切点与切点重合"的循环论证。

> 下次：结论如果**太干净**（0.03s、6/6 全中），先怀疑判据，再高兴。

**3. 能力边界要实测，不要凭印象**

"我能不能上网爬视频"这个问题，猜是没用的。实测：`web_search`/`read_page` 挂了、
PowerShell 与 Python 的 HTTPS 挂了，但 **yt-dlp 能搜 B站、能下载**，
**`read_image` 让我能真的看图**，Node.js 是唯一能过 HTTPS 的通道。
四条可用链路里**一条都不在"搜索引擎"上**。

> 下次：问"有没有工具"时，把**替代路径**一起试了，别在第一个 429 上停下来说没有。

### 技术层踩坑

**4. 击杀横幅的实测位置（本轮最硬的数据）**

1280x720 素材里，横幅占 **y 522~613**（峰值行 523），横向在**画面中部** x380~900；
旧标定 `crop=1280:120:0:600` 只截到 **y600~613 这 14px**，带子里装的主要是技能栏/弹匣/经济。
修正带子：`crop=1280:100:0:520`。右上那条标定**没问题**（横幅不在右上）。

**5. `16.733` 是确凿误报 —— 目视确认是「战术计分板弹出」**

`verify_kill_frames.py` 抽帧可见：16.43 正常对枪、**16.73 起战术面板浮层出现**。
带内洋红占比 0.0000、高频 0.34（对照真击杀 14.73 是 0.017 / 5.82）。
修正标定后该点被正确剔除 —— **这是"新标定更好"的第一个 ground truth。**

**6. 换标定让全部 11 条素材的击杀数从 61 变 53**（`58b8e283` 9→4、`7f0d8287` 5→9）。

**默认值没有改**：换默认等于换掉既有 EDL 的取景依据，必须有 ground truth 才做。
改成 `--band legacy|measured`，默认 legacy，并在文件头写明证据。

**7. 两个小坑**
- `imageio.imwrite` 收到 int16 数组会抛 `KeyError: ((1,1,3),'<i2')` —— 写 PNG 前必须转 uint8。
- `--shots` 指到不存在的文件时，工具**安静地输出一堆 `-`**，看起来像"没有切点数据"。
  已改成显式报错 + 退出码 2。**静默降级比报错更贵。**

**8. 子 agent 独立量出的效果时长，带一个必须一起引用的警告**

基于"完全重复帧"判据：静止段中位 ~167–170ms（5 帧 @30fps）、白闪 50–167ms
（最常见 **33/67/133ms = 1/2/4 帧**）、黑场 33–600ms。
但该判据**同样会命中素材本身静止的画面**（已目视确认 `BV1U1kJBrEd7` @7.97–8.6s 是
观战视角拍不动的角色，不是定格）→ **是上界，不是编辑时长**。
唯一比较可信的是 **33ms 白闪**（1 帧不可能来自素材）。数据：`research/killmoment2.json`。

## 第 5 轮 · 2026-09-13 · 建「手法库」+ 学 B站 教程（续）

**本轮目标**：把已学到的剪辑手法固化成可复用的库，并去 B站 补没学过的。

**结论**：建起 `references/techniques/`（索引 + 来源索引 + 击杀瞬间 + 音频）。
B站 又下 16 条（累计 **31 条**在 `参考视频/教学/`），三条并行挖矿仍在跑。
并且又踩到**同一个根因的第二个变体**（见流程层 11）。

### 方法层经验

**1. 「操作」「手法」「风格」必须分成三种文件**

之前全混在一起，导致「能不能凭空写」这条判断无处安放。现在分开：

| 文件 | 管什么 | 能不能凭空写 |
|---|---|---|
| `editing-rules.md` | **风格**（你自己的片子怎么切） | ❌ 必须从**用户真实成片**归纳 |
| `operations.md` | **操作**（某功能叫什么、在哪、能否自动化） | ✅ 标来源即可 |
| `techniques/` | **手法**（做出某个效果的做法与参数） | ✅ 但**必须带证据等级 L1–L4** |

**2. 证据等级是这份库的地基**

L1 本机实测 / L2 读自教程里的剪映 UI / L3 二手 / L4 本项目策略。
上线这套分级之后，"哪些数字能用"第一次变成**可机械判断**的事 ——
之前只能靠记忆和印象，这正是「闪白 0.1 秒」那类零来源数字能混进来的原因。

**3. ★ 教程 ≠ 成片：两者用途完全不同（本轮最有用的一条）**

- **教程录屏** → 只能用来读**菜单路径**（L2），因为界面是静止的。
- **成片** → 才能用来量**效果时长**（L1）。

我把同一套"重复帧"判据同时跑在两类素材上，结果：

| 视频 | 类型 | "定格"段数 | 最长 |
|---|---|---|---|
| 瓦成片 | 真剪辑 | 4 | 10000ms（显然是静止画面） |
| 剪映教程 | **录屏** | **579 段 / 4715 帧 = 12%** | 2267ms |

**在教程录屏上量效果时长会得到荒谬结果** —— 界面本来就静止。
> 下次：任何"逐帧量效果"的活，先问"这是成片还是录屏"。混用会产出看起来很专业、实际无意义的数字。

**4. 新独立样本印证了老结论**

`BV1fEbK6xEaP`（110s 瓦成片）实测白闪 **67/100/167ms**、黑场 67/467/667ms，
与既有样本（33/67/133ms、33–600ms）**同量级且互相印证**。
独立性很重要：这是第 7 条片子，不是同一条的重复测量。

### 技术层踩坑

**5. 子 agent 的下载会污染仓库根目录**

它把 `_fetch.mjs` / `_research/` 等建在仓库根。**委派任务时必须指定 scratch 落盘位置**，
否则根目录每次都要人工清理（本轮清了两次，第二次是 `_reddit_out.txt`）。

**6. 教学视频里很多根本不给剪映界面**

我抽帧看了 110s 的瓦教程：**前 96 秒全是成品演示 + 口播**，没有剪映面板。
⇒ 这类视频只能当 **L1 素材**（量效果样子），不能产出 L2（菜单路径）。

## 第 6 轮 · 2026-09-14 · 剪映曲库 BGM + 自动击杀判据第二次被打穿

### 方法层经验

**1. ★ 「剪映曲库不能程序化引用」是真的，但**用户的缓存里就有真曲**

`AudioSegment` 只收本地文件（`environment.md` 已记），所以"在草稿里写一条曲库音乐"堵死了。
**但用户在该面板试听/下载过的曲子会落在本机**：

```
%LOCALAPPDATA%\JianyingPro\User Data\Cache\music\<hash>.mp3     ← 音频本体
                                              \<hash>.beat    ← ★ 剪映自己算的拍点
```

`.beat` = `time`(毫秒) + `value`(拍号 1/2/3/4) + `energy`。这是**第一方产物**，
比自己估 BPM 硬得多 —— 于是"切点落在拍上"这件事第一次不需要我再估 BPM。

**坑**：`.beat` 的文件名 hash 和 mp3 的文件名 hash **不是同一个**（3 份里 0 份同名），
只能按「时长 − 末拍点」最近配对。`downLoadcfg` 里有下载台账，可看出先后。

> 下次：**先翻用户本机缓存，再考虑接口**。剪映把"素材"和"素材的元数据"分开存，
> 元数据（拍点/能量/时长）往往比素材本身更有用。

**2. ★★ 自动击杀判据第二次被打穿 —— 而我的新判据也没立住**

`analysis2/kills_mine_measured.json` 进过 EDL、进过成片，看起来"经过这么多轮验证"。
本轮按 `kill-extraction.md` 的纪律做目视核对，撞到：

| 信号报的 | 目视看到 |
|---|---|
| `4c58efb4` **1.433s** | 右上角 **5 个敌人头像全亮** —— **没人阵亡** |
| `b61cc53d` **6.2s** | 只有 **4 个亮**，而 10.0s 是 **5 个** —— 位置对不上 |

连败两次：

| 版本 | 判据 | 结果 |
|---|---|---|
| v1 | 全局亮度阈值（整条 P85 × 0.78） | ❌ 受击态（血条变红）把存活判成阵亡，存活数 2~5 乱跳 |

**结论：v3 只能当"人看台账"的辅助，还不能当自动判据。**
⇒ 这条片子的击杀时刻**仍然来自信号判据**，我只在两次白闪上做了目视确认，

> 不只是"上线前抽查几条"，而是**抽查结果必须能推翻上游清单**。

> **抽查要挑"最可能错"的那条**（最早的时刻、最弱的信号），不是挑最像的。

**3. ★ 「多个片段叠加在同一时刻」会打穿所有按"顺序拼接"写的检查**

白场/黑场是**素材**（`kill-moment.md` §1），所以它们必须是**视频片段**。
但这就让两个既有工具同时得出**假结论**：

| 工具 | 症状 | 真因 |
|---|---|---|
| `tools/verify_shot_order.py` | 报 `✗ white_2f: 0.000@15.37s < 0.000@15.44s` —— "有回跳，就是割裂" | 白场被用了 2 次，`source_in` 都是 0 ⇒ **本来就该回跳**。它不是切点，是**压在切点上的效果素材** |
| `tools/render_preview.py` | 预览里整屏白/黑一大段 | 叠加轨被当主轨顺序拼进去；`-t` 又用 `sum(所有 clips)` ⇒ 15.57s ≠ 真实 15.37s |

两处都改成**只算主轨**（`track` 不以 `ovl_` 开头），总长一律用
`max(start + duration)` 而不是 `sum(duration)`。

> 这是**同一个算术错误的第三次**：
> 第 2 轮是"转场当额外占时 ⇒ 每处转场闪黑"（自检口径：若 `Σ duration < end` 就一定有黑洞），
> 本轮是"叠加轨算进 Σduration ⇒ 成片长度虚长 0.2s"。
> **只要出现"片段可以不按顺序、不互相首尾相接"的结构，`Σ duration` 就不再是长度。**
> ⇒ 以后凡是要"总长"，先问一句：**这些片段是顺序拼接的，还是允许重叠的？**

**4. 剪映云曲库接口在默认环境里是 403，而且不该绕**

### 方法层经验

**1. ★★ 「信号自证不算验证」这条第三次咬人 —— 而这次咬的是我自己**

本轮我先用「洋红占比」在 `b61cc53d` 上找到一段 0.808 的强信号，写了「击杀横幅实测
y30~70、洋红→粉渐变」并据此把该候选的置信度标成 **high**。
**子 agent 独立抽帧后推翻**：

| 我以为 | 实际是 |
|---|---|
| 6.53~7.43s 整屏洋红 = 击杀横幅 | **技能/特效**（横幅应该在每次击杀都出现，但它只出现 1 次） |
| （仓库旧记录）底部洋红带 y522~613 = 击杀横幅 | 与**准星**重合，是**准星命中标记**（紫菱形→洋红心形+放射线） |

> **如果 A 真是 B，它应该在 B 的每一次出现时都出现**。只出现一次就说明 A ≠ B。

**2. ★ 「锚点是可复现的」和「锚点是正确的」是两件事**

HUD 帧间差突变帧很干净、可复现、`--check` 每次一致 —— 但它只证明
「**HUD 在这些帧发生了变化**」，**不证明**「击杀发生在这帧」。
本素材的回合计时是**跳变**更新的（帧 196 时 1:25 → 帧 197 时 1:24），
所以「HUD 更新时间」与「击杀时间」之间隔着一个**无法从画面证明的量**。

⇒ 产出物里如实写了 `confidence=medium` 与「**没有任何一个候选拿到正面证据**」，
并把这句写进交付说明的 §4，而不是把「抽出来一张干净的表」当成结论。

**3. 剪映没有可自动生成的「标记」，但短文字片段能达到同样目的**

实测三条：`pyJianYingDraft` 0.3.0 无 marker 类；本机读入的 `draft_content.json` 里
`time_marks` 是 `null`；扫遍 `%LOCALAPPDATA%\JianyingPro` **没有任何非空 `time_marks` 参考**。
⇒ **不去猜剪映的 marker schema**（猜错的代价是草稿打不开），改用**短文字片段**：
在剪映里它是一段可选中/可拖动/可删除的独立素材，视觉上是带底色框的编号，逐帧核对完全够用。

**4. 「一个素材」是自由度，交付的是可复核的选择**

用户只说「一个单个素材」，11 条里没指定。我按**可核验的依据**选 `b61cc53d`
（信号判据给出的候选最多：10 个），并把「它其实是**观战/直播 HUD 录屏**、
不是第一人称原生素材」这个**特性**连带写进交付说明 —— 这正好是它作为训练样本的价值：
旧判据在它上面会失效，是**压力测试样本**。

### 技术层踩坑

**5. ★ 30fps 下「帧」不是整数微秒 —— 两头取整会系统性错位 ±33µs**

```
F350 理想值 = 11666666.67µs → 草稿里必然存 11666700µs   （+33µs）
F418 理想值 = 13933333.33µs → 草稿里必然存 13933300µs   （−33µs）
```

我第一版**独立校验器**拿「理想帧值」去比草稿的整数微秒，**报出 12 个假问题**。
治法：**只保留一份真值** —— 帧号 → 微秒整数（`round`），EDL 的秒值、台账、校验全部由它反推。

配套口径：**反算帧号必须用 `round`，不能用 `int`**
（`13933300 × 30 / 1e6 = 417.999`，`int()` 截断成 417，实际是 418）。

> ⚠️ 这是本项目**第四次**在同一族问题上翻车（转场当额外占时 / 叠加轨算进 Σduration /
> 亮度差切点 / 现在是帧↔微秒）。**共同点：同一个量在管线里有两套口径。**

**6. PowerShell 的 `Copy-Item -Recurse` 在目标已存在时会套一层同名子目录**

把草稿从工作区拷进剪映目录（第二次）时，目标目录已存在 ⇒ 结果多出
`击杀帧标记_b61cc53d\击杀帧标记_b61cc53d\draft_content.json`，
而**顶层那份仍是旧版**（哈希不一致才发现）。
破法：**逐文件 `Copy-Item -Force`，然后比对 sha256**，别相信「拷贝成功」的回显。

**7. 沙箱仍然挡剪映草稿目录（第 N 次，本轮是「写」）**

`workspace-write` 下 `Copy-Item` 到 `%LOCALAPPDATA%\JianyingPro\…\com.lveditor.draft` 直接
`UnauthorizedAccessException`。按 README 的做法：**先写工作区母本，再单独一次加宽权限拷进去**，
拷完用 **sha256 与母本对账**。

## 第 8 轮 · 2026-09-15 · 用入库证据独立复算击杀帧判据（无素材/无剪映/无网络）

**本轮目标**：在没有原始素材、没装剪映、不联网的机器上，验证「第 7 轮的击杀帧结论

**结论**：**能做，但只做到一半** —— 一条结论独立复现、一条措辞被推翻、

### 方法层经验

**1. ★ 入库的「证据图」分两类，混用必出假结论**

| 类别 | 位置 | 能不能当像素证据 |
|---|---|---|
| **拼接图**（上=整帧，下=按区域叠的帧带） | `verification/killlabels/*.png`（1350x1021 / 1360x1012） | ❌ 不能 |
| **原始区域裁切**，文件名编码区域 `{素材}_t{时间}_{w}x{h}_{x}_{y}_k{放大}` | `verification/frames/*.png` | ✅ 能（按 k 下采样还原） |

我在拼接图上盲测洋红，**多帧都命中同一个 `5x5` 洋红小块 @(848,40)** —— 那是拼接版式的固定元素，
不是画面内容。⇒ **量像素前先问一句「这张图是不是拼出来的」**。
另外 125 张裁切里 **35 张命名不含区域字段**（`4b0460c4_t12.500.png` 这种），
**无法反推区域 ⇒ 等于不可复算**。可复核性是在**出图那一刻**决定的，不是事后补的。

> 下次：**给"证据"定死格式** —— 要么带完整区域编码的原始裁切，要么别放证据目录。

## 第 9 轮 · 2026-09-15 · 音频瞬态判据可行性预研（零素材 / 零剪映 / 零网络）

**本轮目标**：只用入库的 `analysis2/raw/audio_*.json`，回答第 7 轮 §7-3 的待办
「换不依赖 HUD 的信号 —— 击杀音效的音频瞬态」到底做不做得起来。

**结论**：**做不起来**。5 个实验没有一个给出「显著高于随机」的结果；
本轮真正的收获反而在方法层（命中率必须配机会基线、比对前先扫固定滞后）。

### 方法层经验

**1. ★ 命中率必须配「机会基线」，否则容差一大就得到假的 100%**

`b61cc53d` 的 10 个候选，容差 vs 机会基线 vs 命中率：

| 容差 | 机会基线 | 实测命中率 | 二项 p |
|---|---|---|---|
| ±0.03s | 0.156 | 0.10 | 0.816 |
| ±0.05s | 0.259 | 0.20 | 0.776 |
| ±0.10s | 0.519 | 0.30 | 0.957 |
| ±0.25s | **0.953** | **0.973** | 0.921 |

我第一版脚本只打命中率，±0.25s 那格显示 **97.3% ≈ 100%**，看上去像「都命中了」，
实际是被**峰密度（2.6 个/秒）**撑起来的空话。
⇒ 判据：**容差必须远小于平均峰间距（本轮 0.34s）才有分辨力**，否则分母已经饱和。
**报命中率时永远同时报机会基线 —— 这是以后写这类脚本的默认动作。**

**2. ★ 信号太密时「有没有信号」这个统计量本身失效 → 换一个不依赖出峰的统计量**

改用「覆盖候选时刻的 250ms 窗」比「候选时刻 vs 随机时刻」的能量（置换检验 2000 次）：
`flux` p=0.747、`band_db` p=0.703、`rms_db` p=0.087（**3 次比较，Bonferroni 后 0.26，不显著**）。
⇒ 「三次里最小的那个 p」不能直接当结论 —— 这也是**统计口径**问题，
和第 2 轮「转场占时」/ 第 6 轮「叠加轨算进 Σduration」/ 第 7 轮「帧↔微秒」/ 第 8 轮「洋红区域」
是同一族错误的最新一副面孔：**本轮栽在容差、基线、多重比较上。**

**3. ★ 比对两个信号前，先扫一遍固定滞后**

把音频峰整体平移 −1.5~+1.5s，11 条素材的「最佳滞后」是
−0.87 / +0.22 / +1.28 / +0.29 / −0.15 / −1.17 / −0.64 / −0.53 / −0.24 / +0.87 / +1.26s
—— **正负都有**；合并曲线 lag=0 命中 35（随机预期 30.0）。⇒ **没有共同滞后**，
「音频串了时间轴」这个解释被排除掉。

⚠️ 反向陷阱：**301 个滞后里挑最大值本身就会挑到噪声**（10 个标签 × 301 次，期望最大值 7–9）。
⇒ **扫滞后只能用来「排除某个偏移」，不能用来「找最佳对齐」。**

### 技术层踩坑

**4. 口径是「睡在数据里」的，要先量出来再谈结论**

3 行代码从 11 个 JSON 里量出两条硬约束，两条都直接决定判据可行性：

- `peaks_flux` 最小间隔 **恰好 0.20s（11/11 条）** ⇒ 上游做了 200ms 最小距离抑制（上限 5 个/秒）
- `windows_250ms` 窗长恰好 0.25s ⇒ 量化误差 **±125ms ≈ ±3.75 帧**，而击杀帧要求 ±1 帧

⇒ **入库 JSON 里能反推上游算法参数的地方，就是这种「不该这么整齐」的统计量。**

**5. 时长对账 = 最便宜的「同一段素材」证明**

`audio_*.json.duration_s` vs `kills.json.signal_seconds`：11/11 条差 **+0.004 ~ +0.029s**，
且 `source` 路径与 `file` 同名 11/11。⇒ 以后拿到两条不同管线的量，**先把时长和文件名对一遍**再下结论。

**6. GUI 取证在本机是死的（第二次确认，这次给出判据）**

`ProcessIdToSessionId` = 5，但 `EnumWindows` 返回 **0** 个顶层窗口、`GetForegroundWindow` = 0、
`PIL.ImageGrab` 报 `screen grab failed`、`GetSystemMetrics` 却能返回 1707x1067。
⇒ 本机 shell 在**非交互会话**里：**能跑脚本、不能碰桌面**。
剪映面板取证只能由**人在自己的桌面上**做 —— 别再试第三次。

**7. 「上一轮把中间量入库」第三次兑现**

装官方 `.venv`（`requirements.txt` 钉的三个版本）后跑仓库自带校验：

## 第 10 轮 · 2026-09-15 · 素材到手，用原始音轨重做音频判据（第 9 轮的「做不了」被真做了）

**本轮目标**：`原始素材\` 里出现了 11 条原始 mp4（0.46 GB，全部带 AAC 48kHz 音轨），
于是把第 9 轮卡住的那句「音频里到底有没有击杀音效」真正测一遍。

**结论**：**§7-3 不成立**。音频里有明确的强瞬态，但和视频候选**没有可靠的时间对应**；
唯一看着像信号的「音频早 0.2–0.3s」被证明是**挑最大值挑出来的假象**。

### 方法层经验

**1. ★ 「在所有滞后/参数里挑最大值」这件事，必须也算进零假设**

第 9 轮我只写到「扫滞后只能用来排除，不能用来找最佳对齐」，当时没有定量做法。
本轮补上了：**max-statistic 零分布** —— 每个模拟也扫 121 个滞后并取最大值，再比。

| 强度档 | 最佳 lag | 命中 | 零分布 max 均值 / p95 | p |
|---|---|---|---|---|
| ≥p95 | −0.29s | 39 | **37.0 / 42.0** | 0.255 |
| ≥p99 | −0.24s | 16 | **14.4 / 18.0** | 0.251 |

看着很整齐的「音频比视频早 0.25s」，在正确的零假设下 p=0.25，**是噪声**。
⇒ **任何「扫参数挑最好那一格」的结论，都要用 max-statistic 零分布复核一次。**

**2. ★ 强度档位要一起扫：真正该看的是「最强的那些是否最准」**

跨 110 个候选：p95 档比随机高 1.1–1.5 倍（p≈0.03，看着像信号），
但 **p99 档完全没有**（±0.10s 甚至 12 < 期望 15.63）。
若音频瞬态真在追击杀，**最强的应该最准** —— 实际正相反。
⇒ 结论是**段落级共现**（交火段落里音频和候选都多），不是同一时刻的对应；
而且 8 个检验里最小的 p，Bonferroni 后 0.03×8 ≈ **0.13，不成立**。

> 这是第 9 轮那条「命中率要配机会基线」的续集：**光配基线还不够，
> 还要（a）分强度档扫、（b）把多重比较和挑选偏差算进去。**

### 技术层踩坑

**3. 素材是「双层同名目录」解压出来的**

实际路径是 `原始素材\原始素材\*.mp4`，而 `Path("原始素材").glob("*.mp4")` 返回 0 个 ——
第一反应会怀疑是中文路径编码问题，其实是多套了一层。
⇒ **落地素材先 `rglob("*")` 打印一层**，别急着怀疑编码。

**4. 量音频之前先看 RMS 包络，不然会对着寂静段找信号**

- `b61cc53d` 开头 **0.4s 静音**；
- **15.0–22.3s 整段偏静**（第 17/18 秒 RMS 中位 −44.8 / −45.4 dB，p95 瞬态一个都没有），
  而候选 15.967 / 19.1（已知非击杀）/ 21.3 正落在这一段 ⇒ **该段音频本身不提供信息**。

**5. 帧对齐的取法：STFT 窗 1024（21.33ms = 恰好 1 帧@30fps）、步 480（10ms）**

入库摘要的 `frame_ms=21.33 / hop_ms=10` 与本轮一致 ⇒ 反过来证实了它的口径。
ffmpeg 直接走 `imageio-ffmpeg`（仓库 pin 的版本），**解码 29s 只要 0.05s**，
整条流程 11 条素材不到 3 分钟 ⇒ 有素材之后这类实验的边际成本极低。

**6. 模板匹配的坑：不做去均值/白化，等于没有特征**

想用「同一个击杀音效会重复」反推时刻：取 64 个瞬态各 0.3s 的 log 频谱 patch 两两余弦 ——
**中位 0.813、p90 0.847**，所有瞬态彼此都很像，完全没有区分力。
⇒ 要么先减全局均值特征（去公共成分）再算相似度，要么换 MFCC + 段内归一化。本轮没做完，如实记下。

**7. 素材到位后，第 9 轮写下的验收条件自动兑现**

`verify_spec_numbers.py`：无素材时 **37 PASS / 3 FAIL**（3 条全是「素材存在」）→ 有素材后 **41 PASS / 0 FAIL**。
⇒ 「把验收条件写成可执行命令」这件事本身是有效的：条件被独立复核了一次。

## 第 10 轮补充 · 2026-09-15 · 击杀横幅定位修正（换对参照物后，音频判据从 null 变成显著）

**本轮目标**：第 10 轮上半场拿到「音频瞬态 vs 旧候选 = 不成立」就收尾了。
补充这一段是因为**收尾复核时发现参照物本身是错的**，于是重新定位参照物、再测一遍。

**结论**：三件事 ——
① 击杀播报在**右上角**（不是第 7 轮记的底部 `y522~613`，那里是准星命中标记）；
② 拿**独立测得的播报事件**当参照物，音频瞬态 **9/9 组合显著、领先 ≈0.1–0.2s**（max-statistic p=0.004）；
③ 但那个检测器**只覆盖「一批播报里的第一次击杀」**（见第 11 条），所以 ② 是**对齐性**证据，不是准确率。

### 方法层经验

**9. ★ 拿到「两个信号不相关」时，先怀疑参照物，再怀疑信号**

同一个音频特征、同一批素材，只换了参照物：

| 参照物 | 结果 |
|---|---|
| 旧的 HUD 3σ 候选（第 7 轮） | ❌ Bonferroni 后 0.13 不显著，p99 档完全没有 |
| **独立测得的播报事件**（本轮） | ✅ **9/9 组合显著**，音频领先 ≈0.1–0.2s（max-statistic p=0.004） |

⇒ **参照物错了，什么信号都测不出东西。** 以后见到 null，先做一件事：
**换一个独立来源的事件集再测一遍**，别急着给信号判死刑。

**10. ★ 白块质量能可靠回答「有没有」，不能可靠回答「有几条」**

想把「有几条播报」量出来，试了三条路，两条失败：

| 判据 | 结果 |
|---|---|
| 播报条的**颜色**（teal 占比 > 0.15 算一条） | ❌ 场景里 teal 太多，全片条目数在 1~7 之间乱跳（`4b0460c4` 中位 3） |
| 白块质量**按行量化**数条目 | ❌ 同素材内单个条目的 white 在 0.02~0.055 起伏，按行量化在 1↔2 之间抖 6 次，当事件源会造假报 |
| 白块质量回答「**有没有**」（0 vs q） | ✅ 信噪比极高 —— 这就是本轮的检测器 |

⇒ **存在性**和**计数**是两个问题，同一个特征不一定都答得了。

### 技术层踩坑

**11. 播报条目是「追加在下面」的，而检测带只盖得住第一行**

播报每个条目约 26px 高，**新条目追加在已有条目的下面**（最新在最下、最旧在最上）；
检测带 `y56~82` 只有 26px ⇒ **它只看得见第一行 = 最旧的条目**。
于是播报**非空**时新来的击杀**完全不改变**带内值 ——
实测 `4b0460c4` 14.4~16.2s 画面里明明有**两条**，带内 `level` 恒为 **1**（漏掉一次）。

⇒ 本检测器的事件 = 「**播报由空变非空**」≈ 一批播报里的第一次击杀；
条目过期上移的空隙还会变成**假上升沿**；`level ≥ 2` 也不是「两条」，是动画重叠
（`b61cc53d` 全片只有 15 帧 `level ≥ 2`）。

> 这条是**收尾时又看了一眼截图**才发现的。否则它会以「`white ≈ 条目数 × q`、
> 每上一个台阶 = 一次击杀播报」的形式**当成结论写进 `references/`**。

**12. 第 7/8 轮「锚点不稳」的原因：锚点抓到的是紧随其后的洋红特效**

`b61cc53d`：HUD 3σ 锚点 = **帧 196**，紧跟其后的**洋红技能特效**从**帧 197** 起；
而**横幅首现帧是 187（6.2333s）**，比锚点**早 9 帧（300ms）**。
两个机制被同一次「突变」抓到，锚点自然不稳。
⇒ 第 7 轮那条待验证的「**横幅首现帧 = 锚点 + 1**」**被推翻**（真实差值是 9 帧）。

### 方法层经验

**14. ★ 领域知识（用户的一句话）比再加一层图像判据便宜得多**

**15. ★ 先问「这个 UI 属于谁」，再问「它什么时候出现」**

|---|---|---|

并把新表里没有的旧行**补回去**（只跑单条素材也不会删掉别的素材的行）。
⇒ 交付给人用的表，**默认操作必须是「不会丢数据」的那个**，不能靠人记得先备份。

**21. ★ 证据图要一次性回答「填表需要的每一个问题」**

每块图里同时放：**整帧 ×3**（t−0.5s / t / t+0.5s，判断当时在不在交火、有没有敌人）
＋ **徽记区逐帧 8 张**（f−4…f+3，判断徽记从哪一帧开始出现）＋ 左上角标题（t/帧号/段长/peak）。
⇒ 标注者不需要回去翻原片。**给人省下的每一步，都要先由交付方想到**；
少放一行，成本就整批转嫁到人身上。

**22. ★ 交付包要在「收件方的配置」下验证，不是在自己的配置下**

本轮的往返验证**第一次是 FAIL**，值得留档：本仓库早就用 **local** 的 `core.autocrlf=false`
覆盖了 **system 级的 `true`**，所以本机一切正常；而 `git clone` 出来的验证仓库
**继承 system=true**，于是 `review.csv`（当时是 CRLF）在 `git am` 时被**归一化成 LF**
（**1824 → 1781 字节**，正好是 43 个 CRLF），tree 就不一致了。

⇒ 两条：

- **验证环境要模拟对方**（`git clone` 出来的干净仓库正好是更严的那个），
  不要用「已经按我的习惯配过」的环境去验 —— 那只能证明「在我机器上没问题」；
- **仓库里不要有 CRLF 文件**。这是第 9 轮那条的加强版：上次的凶手是 **Python 的默认换行**，
  这次是 **git 的 `core.autocrlf`**，两次都只影响「全仓库唯一那个 CRLF 文件」。
